# AGENTS.md — Руководство для Codex по проекту Odoo Community (внутренний контур)

## О проекте
Вы находитесь в корне форка официального репозитория **Odoo Community** (https://github.com/odoo/odoo).  
Проект разворачивается во внутреннем контуре предприятия на территории РФ, поэтому могут использоваться модули локализации (`l10n_ru`) и собственные доработки.  
Ваша задача как AI-агента — помогать разработчику в анализе, доработке, создании и интеграции модулей, строго следуя официальным рекомендациям Odoo.

## Роль и правила поведения
- Вы ассистент по разработке Odoo, знающий структуру проекта, модели, представления, ORM, бизнес-логику.
- Вы всегда руководствуетесь [официальными Coding Guidelines Odoo](https://www.odoo.com/documentation/18.0/contributing/development/coding_guidelines.html) (актуальная стабильная версия).
- Отвечайте конкретно, с примерами кода на Python и XML, используя реальные модули из `addons/` или `custom_addons`.
- Перед генерацией кода проанализируйте существующую реализацию: не дублируйте логику, используйте наследование (`inherit`).
- Никогда не изменяйте код ядра (`odoo/` и стандартные модули `addons/` напрямую), только через механизмы наследования или создание новых модулей.
- Предлагайте решения с учётом безопасности, производительности и переносимости между версиями.

## Структура каталогов
- **`odoo/`** — ядро фреймворка: ORM, веб-клиент, серверные утилиты. Здесь лежат `models.py`, `fields.py`, `api.py`, `http.py`, инструменты командной строки.
- **`addons/`** — стандартные модули сообщества (`base`, `crm`, `sale`, `stock`, `account`, `purchase`, `hr` и т. д.). Меняются только через наследование.
- **`custom_addons/`** — собственные и доработанные модули предприятия, а также модули OCA (например, `oca_addons/`). Именно сюда нужно помещать новые модули.
- **`doc/`** — документация Odoo.
- **`debian/`**, **`setup/`** — вспомогательные файлы для сборки, не требуют частого вмешательства.
- **`odoo.conf`** — конфигурационный файл сервера. Пути к модулям перечислены в опции `addons_path` (добавляйте туда новые директории с модулями при необходимости).

## Типичный модуль Odoo
Каждый модуль (например, `custom_addons/my_module/`) содержит:
- **`__manifest__.py`** — метаданные: имя, версия, зависимости, категория, данные, демо-данные.
- **`models/`** — классы бизнес-объектов. Наследуются от `models.Model` (с постоянными записями) или `models.TransientModel` (временные, wizard). Файл `__init__.py` обязателен.
- **`views/`** — XML-определения интерфейса: формы, деревья, канбаны, поиск, действия (ir.actions.act_window), меню.
- **`security/`** — `ir.model.access.csv` (права доступа на уровне модели), `security.xml` (записи групп и правил записей).
- **`data/`** — начальные данные (загружаются при установке), шаблоны писем, cron-задачи.
- **`static/`** — JS, CSS, изображения, файлы локализации (`description/`, `src/`).
- **`i18n/`** — файлы переводов `.po` / `.pot`.
- **`tests/`** — модульные тесты Python.
- **`wizards/`** — временные всплывающие окна (тоже модели, но TransientModel).
- **`report/`** — шаблоны QWeb-отчётов.

## Ключевые соглашения кодирования (согласно Odoo Guidelines)
- **Python (PEP8 с дополнениями Odoo)**:
  - Имена моделей: единственное число, CamelCase, с префиксом модуля (например, `my.module` → `class MyModel(models.Model)`, поле `name` указывается всегда.
  - Имена полей, методов, переменных: `snake_case`.
  - Обязательное документирование методов и сложной логики.
  - Использование декораторов API: `@api.model`, `@api.depends`, `@api.onchange`, `@api.constrains`.
  - Наследование: `_inherit = 'existing.model'` без перезаписи всего класса, добавляйте и переопределяйте только необходимое.
  - Запрещено использовать `*` импорты.
- **XML**:
  - Идентификаторы (id) представлений, действий, групп должны быть уникальны, с префиксом модуля (например, `my_module.view_model_form`).
  - Соблюдайте иерархию меню и действий.
  - Для наследования представлений используйте `inherit_id` с XPath или указанием `expr`.
- **Безопасность**:
  - Для каждой модели должен быть создан `ir.model.access.csv` с правами для групп.
  - Используйте `groups="..."` в представлениях для ограничения видимости.
  - Глобальные правила записей (record rules) задаются в XML.
- **Данные**:
  - Файлы с начальными данными размещайте в `data/`, подключайте в манифесте (`'data': [...]`).
  - Для демо-данных используйте флаг `'demo': [...]`.

## Разработка нового модуля
1. Создайте подкаталог в `custom_addons/<module_name>/`.
2. Напишите минимальный `__manifest__.py`:
   ```python
   {
       'name': 'Название модуля',
       'version': '18.0.1.0.0',
       'category': 'Sales',
       'summary': 'Краткое описание',
       'depends': ['base', 'sale'],
       'data': [
           'security/ir.model.access.csv',
           'views/my_model_views.xml',
       ],
       'installable': True,
       'application': False,
       'auto_install': False,
   }
   ```
3. Создайте модель в `models/my_model.py` (наследование от `models.Model`), добавьте поля.
4. Определите представления в `views/`.
5. Пропишите права доступа в `security/ir.model.access.csv`.
6. Обновите список модулей и установите через интерфейс или командную строку (`-u my_module`).
*Используйте команду* `odoo-bin scaffold <module_name> <destination>` для генерации каркаса.

## Доработка существующих модулей (CRM, Sales, Inventory и др.)
- **Никогда не редактируйте исходники в `addons/`**. Создайте свой модуль, который зависит от нужного (например, `depends': ['crm']`), и наследуйте модели/представления.
- Добавление поля к стандартной модели:
  ```python
  class ResPartner(models.Model):
      _inherit = 'res.partner'
      my_field = fields.Char(string='Моё поле')
  ```
- Изменение представления: в XML используйте `inherit_id` с указанием внешнего идентификатора стандартного представления и добавляйте свои поля/атрибуты через XPath.
- Переопределение метода: вызывайте `super()` для сохранения исходного поведения, если иное не требуется.
- Если необходимо изменить workflow (например, в `sale.order`), проверьте наличие хуков `_action_confirm` или соответствующих методов, переопределяйте аккуратно.

## Интеграция модулей OCA (Odoo Community Association)
- Модули OCA обычно добавляются в отдельную директорию, например `custom_addons/oca/` или подключаются как подмодули с собственным путём.
- Перед интеграцией проверьте совместимость версий (Odoo 18.0 → соответствующие ветки OCA).
- Убедитесь, что все зависимости OCA-модуля (как внутренние, так и внешние библиотеки) выполнены. Используйте `pip install` для Python-зависимостей.
- Модули OCA могут добавлять новые модели/представления; для включения их функциональности достаточно установить модуль и добавить путь в `addons_path`.
- При возникновении конфликтов с стандартными модулями используйте мосты (модули `connector`, `*_adapter`) либо наследуйте логику OCA в собственном модуле.

## Работа с ядром (`odoo/`)
- Изменения в `odoo/` допустимы только в крайних случаях (исправление критических багов, отсутствующих в официальном репозитории) и только с детальным документированием в коммите.
- Все кастомные расширения фреймворка предпочтительнее делать через механизмы monkey-patching на уровне модуля (`odoo.addons.base.models.*`), но лучше через собственные надстройки, использующие публичный API.
- При обновлении форка с upstream ваши изменения в ядре должны быть пере-базированы без конфликтов.

## Тестирование
- Модули должны содержать тесты в `tests/`. Используйте `odoo.tests.common.TransactionCase` или `SavepointCase`.
- Запуск тестов: `odoo-bin --test-enable -u my_module --stop-after-init`.
- Проверяйте, что новые поля не ломают существующие представления и процессы.

## Локализация и РФ-специфика
- Для соответствия законодательству РФ используйте модуль `l10n_ru` из стандартных `addons/` или его OCA-версию.
- Добавляйте недостающие поля/отчеты в собственном модуле, наследующем `l10n_ru`.
- Переводы на русский язык: поместите файлы в `i18n/ru.po`. Для новых модулей экспортируйте шаблон через интерфейс или командой `odoo-bin export-i18n`.

## Как вы помогаете (инструкция для агента)
1. **Объяснение структуры** — покажите, где что лежит, как связаны модули.
2. **Генерация кода** — только после анализа существующей логики, с пояснениями.
3. **Рефакторинг** — предлагайте улучшения, следуя DRY, KISS и Odoo-конвенциям.
4. **Решение проблем** — при ошибках читайте трейсбек, проверяйте зависимости, права доступа, корректность XML-идентификаторов.
5. **Ссылайтесь на документацию** — используйте официальные источники, когда это уместно.
6. **Предупреждайте о рисках** — например, изменение стандартных рабочих процессов может нарушить связанные модули.

## Коммиты

Согласно официальному руководству Odoo 18 Git Guidelines, сообщения коммитов должны строго следовать определенной структуре, состоящей из четырех обязательных частей: тега, имени модуля, краткого описания и детального описания.

### 📋 Структура сообщения

[TAG] модуль: короткое описание

Полное описание отвечает на вопросы "зачем?" и "что?", а не "как?".

Используйте код с осторожностью.

### 🏷️ Обязательные теги (Tags)

Вы должны классифицировать свой коммит с помощью одного из следующих префиксов:

- [FIX] для исправления ошибок: в основном используется в стабильной версии, но также подходит для исправления недавних ошибок в версии для разработчиков;
- [REF] для рефакторинга: когда функция существенно переписывается;
- [ADD] для добавления новых модулей;
- [REM] для удаления ресурсов: удаление неиспользуемого кода, удаление представлений, удаление модулей и т. д.;
- [REV] для отмены коммитов: если коммит вызывает проблемы или нежелателен для отмены, он выполняется с использованием этого тега;
- [MOV] для перемещения файлов: используйте команду `git move` и не изменяйте содержимое перемещаемого файла, иначе Git может потерять отслеживание и историю файла; также используется при перемещении кода из одного файла в другой;
- [REL] для коммитов релизов: новые основные или дополнительные стабильные версии;
- [IMP] для улучшений: большинство изменений, внесенных в версию для разработчиков, представляют собой постепенные улучшения, не связанные с другим тегом;
- [MERGE] для коммитов слияния: используется при переносе исправлений ошибок, а также в качестве основного коммита для функций, включающих несколько отдельных коммитов;
- [CLA] за подписание лицензии Odoo Individual Contributor License;
- [I18N] для изменений в файлах перевода;
- [PERF] для патчей повышения производительности;
- [CLN] для очистки кода;
- [LINT] для проходов проверки синтаксиса;
